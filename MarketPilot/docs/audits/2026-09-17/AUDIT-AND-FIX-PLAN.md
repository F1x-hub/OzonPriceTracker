# MarketPilot: визуальный, технический и продуктовый аудит

Дата: 17 сентября 2026. Статус: аудит выполнен; P1 и основные P2-исправления реализованы, live-проверки расширения остаются отдельным финальным этапом.

## Метод и границы доказательств

Проверены текущие исходники во вложенной папке MarketPilot, manifest, формы, сообщения, хранение, планировщик и тесты. Выполнен npm test: проходит. Локальный Chromium/Playwright отрисовал актуальные файлы на ширинах 1440, 1024, 768 и 390 px. Chrome API подменены тестовым объектом; реальные данные пользователя, магазины, AI, отправка ответов и уведомления не использовались.

Скриншоты dashboard-*.png, settings*.png, popup.png и observations.json находятся рядом с этим отчётом. inspect.cjs воспроизводит проверку из корня репозитория; путь к Playwright локальный и потребует настройки на другом компьютере. Это браузерные UI-доказательства, не подтверждение работы установленного расширения. Старый пользовательский скриншот не доказывает, что установлена устаревшая версия: исходная CSS-ошибка сама объясняла видимость hidden-формы.

Применены frontend-design, web-quality-audit, emil-design-eng и webapp-testing. React/Next.js и shadcn в package.json отсутствуют: специфичные для них оптимизации и миграция не требуются для исправления найденного. SEO для внутренних страниц расширения не является задачей. Lighthouse, axe, реальные Core Web Vitals и screen reader не запускались; оценки соответствия стандартам не заявляются.

## Итог

Визуальная оболочка и рабочее разделение теперь собраны вокруг `MarketPilot`: экран «Товары» отвечает за Ozon-мониторинг, «Сбор» — за WB/Citilink, «Задания» — за фоновые операции. Командные ошибки, отсутствие цены и повторная ссылка обрабатываются правдиво. Реальные магазины, Seller, уведомления и экспорт всё ещё требуют проверки в установленном расширении.

Сохраняем: самостоятельную страницу расширения, ручной URL Ozon, отдельные видимые поля WB/Citilink, Shadow DOM Ozon, ленивый XLSX, фоновые команды, базовую клавиатурную фокусировку и reduced motion.

## Что исправлено после аудита

- `core/storage.js` отклоняет ответы `{status: "error"}`, а формы сохраняют введённые артикулы при ошибке или `already_running`.
- `dashboard.js` различает `null`-цену и нулевую цену, добавляет состояния jobs для проверки Ozon, таблицы последних WB/Citilink результатов и ARIA-связи форм.
- В «Заданиях» появились явные действия очистки результатов WB/Citilink рядом с XLSX-экспортом.
- `dashboard.html` вынес разовый сбор в отдельный маршрут «Сбор»; на «Товары» остались URL Ozon, цель и таблица мониторинга.
- `dashboard.css` устраняет min-content растяжение мобильного sidebar, применяет общий `[hidden]` и оставляет горизонтальную прокрутку только внутри таблиц.
- `background.js` сохраняет ID/дату/наблюдение при повторном URL, сериализует merge цен и DeepSeek-статистику, проверяет актуальную запись перед уведомлением и выбирает content-message адаптер Ozon или WB.
- В настройках MarketPilot добавлен блок «Баланс и использование»: последний ответ DeepSeek с валютой и временем проверки, успешные запросы, входные/выходные/общие токены, расчётный расход CNY, ручное обновление баланса и сброс статистики; UI использует существующие `deepseek_check_balance` и `deepseek_reset_stats`.
- Модели DeepSeek обновлены: новый default `deepseek-flash` (DeepSeek-V4.1-Flash), `deepseek-v4-pro`, отдельные режим и сила мышления; старые `deepseek-chat`/`deepseek-reasoner` мигрируют на Flash с сохранением смысла через thinking mode.
- Ozon-парсер отклоняет цену без `₽`; legacy-рендер отслеживаемых товаров больше не вставляет title и URL через HTML-строку.
- `npm test`, `npm run build` и локальный Playwright-аудит после изменений проходят; на 390/768/1024/1440 body layout не расширяется, `null` показывает «Ожидание», controlled `{status:"error"}` оставляет ввод, настройки показывают тестовый баланс `12,34 USD`, 7 запросов, 2 000 токенов и `¥0.123`.

Остаются: live reload unpacked extension, реальные карточки магазинов, перезапуск worker, экспорт XLSX и согласованный Seller submit. После мобильного режима таблиц `body.scrollWidth` и `documentElement.scrollWidth` совпадают с viewport; nav остаётся отдельным горизонтально прокручиваемым списком.

## Технические находки по исходникам

### P1: корректность и сохранность данных

- T1. background.js checkPrices читает свежий trackedItems и пишет результат напрямую, вне trackedItemsWriteQueue. Между чтением и записью может пройти удаление/добавление. Очередь upsert/remove не защищает этот путь. Перенести merge в тот же владелец записи; проверить управляемую гонку.
- T2. background.js upsertTrackedItem объединяет существующую запись с входным объектом, включая новый id, title=url, lastPrice=null и addedAt. Повторный ручной ввод способен заменить идентификатор и накопленные сведения. Сохранять идентичность, наблюдения и дату создания; команда редактирования цели меняет только цель/тип цены.
- T3. Проверка цен принимает отсутствие цены без увеличения failed; задача может закончиться done без результата. checkSingleItem ждёт фиксированные 4 секунды, а content.js извлекает Ozon независимо от магазина. Для каждого магазина нужен собственный адаптер и результат ok/not_found/unsupported/error.
- T4. Поддержка ozon.com добавлена, но currency нигде не моделируется: UI всегда ₽, парсеры удаляют дробный разделитель или обрезают дробь. Для строки «19,33 ₾» озон-виджет получает 1933, старый парсер — 19. Это вывод из кода, не свежий сетевой тест. До реализации валют запрещать мониторинг нерублёвой цены с понятным объяснением; не сравнивать разные валюты.
- T5. Старый popup.js:263 вставляет внешние title/url в innerHTML без экранирования. Совместимый экран всё ещё доступен из dashboard. Перевести на textContent/безопасные атрибуты и URL allowlist. Подтверждён небезопасный HTML sink; исполнение скрипта/эксплуатация CSP не доказаны.
- T6. core/storage.js openDashboard при существующей вкладке меняет только active: запрошенный hash настроек теряется. Обновлять URL и активировать нужное окно.
- T7. Состояния заданий сохраняются, но это не полноценная возобновляемая очередь. Reconcile вызывается на onStartup браузера; автоматического продолжения с сохранённой позиции нет. Чётко определить interrupted и ручное продолжение только неисполненных read-only элементов. Seller unknown автоматически не повторять.

### P2: сценарии, архитектура и качество

- T8. renderProducts показывает только trackedItems; wbLastResults/citilinkLastResults доступны для экспорта, но не для просмотра таблицей в новом dashboard. Фильтры WB/Citilink могут создавать впечатление пропавших результатов.
- T9. При любом обновлении статусов refresh заново строит таблицу и перезаписывает checkInterval. Несохранённая цель/интервал и фокус могут потеряться. Нужны черновики и адресное обновление.
- T10. AI-статистика в background.js остаётся read-modify-write без общей очереди; параллельные запросы могут потерять суммы.
- T11. Seller остаётся файлом 2869 строк, background — 1376, legacy popup — 1295. Вынесение DOM helpers не завершает разделение reviews/questions/rich и адаптеров магазинов.
- T12. Jobs не показывает priceCheckStatus, хотя общий счётчик его учитывает. phase checking отсутствует в словаре. stale рассчитывается только при рендере, поэтому остановившееся задание не обязательно своевременно получит предупреждение.
- T13. Локальные ошибки формы не привязаны через aria-describedby/aria-invalid; уведомление исчезает через 3,6 секунды, включая ошибки. Target editor содержит кнопку внутри label. Нужны семантические группы, постоянные ошибки, отдельные подписи и управление фокусом.
- T14. npm test проверяет синтаксис, строки в исходниках и часть VM-контрактов, но проходит при всех четырёх подтверждённых UI-сбоях. Нужны проверки поведения, а не дополнительных идентификаторов в HTML.
- T15. README и правила проекта описывают старый popup как основной; DEVELOPMENT содержит путь с OzonController. Две директории MarketPilot и установка source/dist создают путаницу. Описать единый путь загрузки и процедуру reload.
- T16. Часть возможностей ещё спрятана в legacy: шаблоны, дополнительные AI-настройки и связанные операции. Нужна матрица функционального паритета до удаления legacy.

## Дизайнерское направление

MarketPilot — рабочий инструмент для повседневного управления товарами. Основная визуальная единица — строка товара или задания с названием магазина и ясным состоянием, а не декоративная карточка.

| Before / сейчас | After / план | Зачем |
| --- | --- | --- |
| Три большие формы и счётчики над таблицей | Компактный ввод Ozon в мониторинге; раздел «Сбор товаров» с двумя явными колонками WB/Citilink и результатами | Сохранить удобный ручной ввод и быстро видеть результат |

| Тексты 10–13 px, разные шрифты textarea/контролов | Основной текст 14 px, подписи 12–13, данные 13–14; единый системный sans-serif, tabular nums | Читаемость и стабильность таблиц |

| Расширенные функции открывают старый popup | Все настройки и шаблоны в dashboard после переноса паритета | Один понятный центр управления |

Предлагаемые токены: canvas #F5F7FA, surface #FFFFFF, text #172033, muted #596579, accent #3157C8; semantic success #16835B/error #B42318. Никаких анимаций, задерживающих ввод.

## План исправления и приёмка

### Этап 1. Правдивые состояния и данные — P1
1. Исправить контракт sendCommand и все вызывающие стороны. Не очищать ввод при отказе/дубликате.
2. Исправить null-цены, сохранить id и историю при повторной ссылке.
3. Включить merge мониторинга в очередь, исключить уведомления для удалённых/изменённых записей по устаревшему снимку.
4. Развести ошибки извлечения, валюты, адаптеры Ozon/WB. До валютной поддержки явно отклонять несовместимую валюту.
5. Убрать небезопасную HTML-интерполяцию в legacy; исправить открытие нужного dashboard hash.
Приёмка: controlled error остаётся ошибкой; введённые данные сохраняются; повторный URL не меняет id/lastPrice; null не равен нулю; гонка remove/check не возвращает товар; нерублёвая цена не сравнивается с рублёвой целью.

### Этап 2. Компоновка и доступность — P1/P2
1. Устранить overflow и единообразно применять hidden.
2. Зафиксировать структуру: мониторинг/товары Ozon, сбор WB/Citilink, задания, Seller, настройки.
3. Сохранить обе отдельные формы артикулов с видимыми подписями; добавить таблицы результатов и экспорт рядом.
4. Уплотнить popup, убрать лишний контекст, сохранить ручной URL и быстрые переходы.
5. Унифицировать типографику, поля, ошибки, focus, disabled/loading; сохранять черновики на фоновых событиях.
Приёмка: 390/768/1024/1440 px без горизонтальной прокрутки документа, таблица прокручивается внутри; 200% zoom; клавиатурный проход; hidden не виден/не фокусируется; фоновые статусы не сбрасывают ввод.

### Этап 3. Завершение модульности — P2
1. Выделить marketplace adapters: URL, capability, parser, collector; убрать смешанный content.js.
2. Выделить background repositories, command handlers, jobs и AI gateway с едиными контрактами.
3. Разделить Seller reviews/questions/rich; документировать подтверждение/unknown, очистку слушателей и остановку маршрута.
4. Перенести недостающие настройки/шаблоны и только после матрицы паритета убрать legacy popup.
5. Проверить масштабируемость тестовым адаптером: новый магазин добавляется без правок существующих парсеров и копирования очереди.
Приёмка: реестр направляет выполнение; один владелец shared state; неизвестный результат отправки не повторяется; legacy больше не требуется для пользовательских возможностей.
Переход на React/shadcn/TypeScript не является условием этого этапа. Отдельное решение нужно только при конкретной выгоде, а не ради замены стека.

### Этап 4. Проверки и документация
1. Добавить браузерные регрессии по U1–U4, формы с ошибками/дубликатами и draft preservation.
2. VM-тесты гонок, идентичности товара, ошибок парсера, прерывания задач, параллельных AI-сумм.
3. Актуализировать существующие инструкции установки и матрицу возможностей; явно разделить мониторинг, разовый сбор и экспорт.
4. В самом конце: reload unpacked extension, реальные карточки Ozon/WB/Citilink, sleep/restart worker, экспорт и открытие XLSX.
5. Отправка Seller — отдельный согласованный тест конкретного объекта; read-only аудит её не разрешает.
Приёмка: npm checks плюс сохранённые браузерные доказательства; недоступные сайты обозначены как непроверенные, не как успешные.

Рекомендуемый порядок: этап 1, этап 2, этап 3, этап 4. Работа оценивается завершённой по критериям, а не по наличию файлов и зелёному синтаксису.
