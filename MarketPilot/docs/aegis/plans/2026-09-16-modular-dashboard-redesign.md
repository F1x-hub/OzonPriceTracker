# Модульное расширение и отдельный дашборд

Дата: 2026-09-16. Статус: статический срез реализован; durable jobs, Seller lifecycle, schema migration, lazy export, command ownership и Ozon `.com` host contract внедрены. Финальный live read-only проход частично выполнен; оставшиеся проверки требуют ручного reload unpacked extension или снятия browser-control ограничений.

## 1. Цель и границы

Превратить набор инструментов Ozon/Wildberries/Citilink в расширяемое рабочее приложение. Оставить popup для контекста текущей страницы и быстрых действий. Перенести управление, таблицы, настройки и историю на отдельную страницу расширения.

План основан на текущих исходниках, manifest.json, README.md и `.agents/rules/agent.md`. Последний требует выполнять изменения только внутри `MarketPilot/`. Исходный Git worktree перед аудитом чистый. Реализация и work-record этой задачи остаются внутри `MarketPilot/`.

Сохранить текущие пользовательские возможности и данные: мониторинг Ozon, сбор цен WB, сбор Citilink и экспорт для Avito, шаблоны ответов, AI-вопросы и отзывы, массовое заполнение Rich-контента, историю уведомлений и AI-настройки. Расширять поддержку магазинов постепенно: одинаковое оформление не означает одинаковые возможности.

Не входят в первую переделку: сервер, облачная синхронизация, аккаунты расширения, магазин загружаемых плагинов, новые реальные маркетплейсы, автоматическая публикация объявлений Avito, автоматическое сопоставление одного товара между магазинами.

## 3. Архитектурное решение

Нужны две независимые оси: **магазины** отвечают за особенности сайта, **функции** — за сценарии пользователя. Простого разнесения файлов по `ozon/`, `wb/`, `citilink/` недостаточно: очереди, экспорт и AI иначе будут копироваться.

### Владельцы

- `platform/`: Chrome API, сообщения, создание и закрытие служебных вкладок, разрешения, уведомления.
- `background/`: обработка команд, планирование, задания и единственная запись общего состояния.
- `storage/`: версии данных, репозитории, миграции, последовательные изменения и резервная копия.
- `features/`: мониторинг, сбор товаров, ответы, Rich-контент, AI, экспорт. Не содержат CSS-селекторов магазинов.
- `marketplaces/`: распознавание страниц, извлечение данных, возможности магазина и DOM-действия. Не управляют общим расписанием и навигацией дашборда.
- `entrypoints/`: запуск service worker, popup, дашборда и content scripts; только подключение нужных модулей.
- `ui/`: общие компоненты, токены, состояния загрузки и ошибок.

UI отправляет команды фону и получает снимки состояния. Content scripts читают DOM, исполняют адресованные им шаги и возвращают результат. Контекст документа не хранится в фоне как DOM-ссылка.

Фон может вызывать DOM-исполнитель только через проверенный `tabId` и текущую сессию документа. Дашборд не обещает работать с кабинетом продавца при закрытой вкладке или отсутствующей авторизации.

### Предлагаемый стек

TypeScript для контрактов и логики; Vite для нескольких точек входа MV3; React и shadcn/ui для дашборда и popup. Content scripts остаются лёгкими TypeScript-модулями с DOM/Shadow DOM, без обязательного React runtime на каждом сайте. Next.js и сервер здесь не нужны.

Это рекомендуемый выбор для новой реализации, а не требование текущего проекта. Сначала проверить небольшой MV3 build: статические ресурсы, CSP, отдельные content bundles и service worker. Версии пакетов закрепить при реализации; не вписывать неподтверждённые «последние» версии в план.

### Структура


## 4. Контракт магазина и добавление нового

Статический реестр поставляемых адаптеров. Никакой загрузки исполняемого кода с сервера.

Описание магазина содержит `id`, название, домены, маршруты, контексты и поддерживаемые операции. Метаданные, доступные UI, отделены от DOM-кода, чтобы popup не импортировал все парсеры.

Возможности задаются отдельно: `readProduct`, `readPrices`, `collectProducts`, `replyToReviews`, `replyToQuestions`, `fillRichContent`. Мониторинг становится доступен только при поддержке получения цен и соответствующего фонового сценария. Нельзя показывать неработающую функцию только потому, что другой магазин её умеет.

Первоначальное соответствие текущему поведению:

| Контекст | Переносимые возможности |
| --- | --- |
| Ozon, карточка покупателя | Товар, варианты цены, мониторинг, виджет |
| Ozon Seller | Ответы на отзывы/вопросы, Rich-контент |
| Wildberries | Сбор вариантов цены по артикулам, экспорт |
| Citilink | Сбор карточки/фото/характеристик, необязательная генерация описания, экспорт |

Ozon Seller — отдельный контекст внутри Ozon, с отдельными маршрутами и исполнителем. Avito пока является форматом назначения экспорта, а не подключённым магазином.

Минимальные общие данные:

- `ProductRef`: `marketplaceId`, `externalId`, нормализованный `url`, при необходимости идентификатор варианта товара.
- `ProductSnapshot`: ссылка на товар, название, фото, характеристики, `collectedAt`, источник и предупреждения.
- `PriceQuote`: сумма в минимальных денежных единицах, валюта, вид цены, условия её применения, время получения. Цена Ozon Банка и цена WB Кошелька не считаются безусловной обычной ценой.
- `TrackingRule`: ID, ссылка на товар, выбранный вид цены, целевая сумма, статус и ревизия.
- `Job`: ID, магазин, операция, список элементов/курсор, статус, результаты, ошибки, время обновления и привязка к вкладке для DOM-операций.
- `OperationResult`: success / error / unknown с кодом причины; отсутствие цены не превращается в ноль.

Для неизвестных пока операций не строить универсальную DSL. Специфичные поля хранить в типизированных расширениях конкретной функции.

Порядок добавления следующего магазина:

1. Добавить папку с definition, парсером и фикстурами реального DOM без личных данных.
2. Объявить контексты и действительно реализованные возможности.
3. Подключить запись реестра и content entrypoint; собрать необходимые manifest matches/ресурсы из декларации.
4. Добавить DOM-исполнитель только для новых поддержанных операций.
5. Пройти общие контрактные тесты и проверку на живой странице.

Критерий модульности: новый магазин, реализующий уже существующие возможности, не требует изменения очереди, репозитория данных и общих экранов. Новая принципиальная возможность закономерно потребует нового feature-контракта.

## 5. Задания, данные и безопасность

### Задания

- Состояния: queued, running, paused, waiting-for-tab, succeeded, partially-failed, failed, cancelled; для отдельного отправляемого ответа также submitting, confirmed, unknown.
- Сохранять вход задания, завершённые элементы и контрольную точку после каждого шага. Повторное открытие popup/дашборда только подключается к существующему заданию.
- Фон восстанавливает задания при старте и событиях планировщика. Просроченное running проверяется и переводится в подходящее состояние, а не навсегда остаётся «в работе».
- Одновременно выполнять ограниченное число операций; не допускать двух DOM-заданий на одной seller-вкладке. Повторный клик запуска не создаёт дубликат.
- Пауза означает остановку перед следующим безопасным шагом; уже отправленный запрос нельзя объявлять отменённым без проверки результата.
- Read-only сбор допускает ограниченные повторы с задержкой. Отправка ответа с неопределённым исходом автоматически не повторяется: сначала проверить состояние на сайте.
- При закрытии/смене seller-вкладки остановить шаги, показать причину и возможность переподключения. После навигации заново проверить идентификатор отзыва/вопроса.
- Служебные вкладки закрывать в `finally`, различать их от пользовательских. При восстановлении сверять владельца задания, URL и идентичность вкладки.
- UI прогресса показывает отдельно успешные, пропущенные и ошибочные элементы. «Завершено» не означает «все успешно».

Обоснование восстановления: Chrome может завершить extension service worker; глобальные переменные не переживают его остановку. Поэтому состояние задания должно храниться вне памяти процесса. [Chrome: lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

### Хранение и миграция

В первой версии оставить `chrome.storage.local`, добавив версию схемы, ограничение истории и единый слой записи. IndexedDB вводить только при подтверждённых требованиях к объёму/транзакциям, не вместе с каждым остальным изменением.

1. Инвентаризировать все ключи, включая позиции виджетов, задержки, модель, промпты, курсы/баланс и статистику.
2. Создать резервный снимок старых данных внутри расширения; не включать ключ AI в обычный экспорт или журнал.
3. Проверить свободное место до дублирования данных. При ошибке quota не менять маркер активной схемы.
4. Преобразовать `trackedItems`, `wbLastResults`, `citilinkLastResults`, `notificationHistory`, `ozonReplyTemplates`, `ozonReplySettings` и `deepseek*` в новый формат. Сохранить идентификаторы и пользовательские значения.
5. Сначала записать и проверить новую схему, затем переключить активную версию. Миграция повторяемая и восстанавливается после прерывания.
6. Старые ключи не удалять в том же шаге. Их удаление — отдельный этап после проверки миграции и окончания периода отката.
7. Пока действует совместимость, старые команды переводить в новые обработчики; не вести две независимые копии бизнес-логики и не оставлять два активных писателя.

Один фон-владелец сам по себе не предотвращает гонки async-обработчиков. Нужны очередь изменений по сущности, ревизии и проверка актуальности перед применением результата. Ответ проверки цены не должен восстанавливать удалённую пользователем запись.

Контракт сообщений: версия, ID запроса, команда, валидируемые данные и структурированный ответ. Проверять отправителя, домен/контекст, `tabId`, размеры и формат входа. Не принимать произвольный URL для привилегированной фоновой загрузки.

Ключ DeepSeek нужен только фоновому API-клиенту; content scripts получают разрешённые настройки и результаты. После перевода всех чтений ограничить прямой доступ content scripts к storage через поддержанный Chrome механизм `setAccessLevel`. Это ограничение доступа, не шифрование. [Chrome: storage](https://developer.chrome.com/docs/extensions/reference/api/storage).

### AI и экспорт

- Общий AI-сервис; DeepSeek — первая реализация, без добавления других провайдеров в этот этап.
- Сценарии промптов отдельно: вопросы, отзывы, описание объявления. Шаблоны по умолчанию определены один раз.
- Сбор Citilink работает без AI-ключа. Генерация запускается отдельно, её ошибка не удаляет собранную карточку.
- Расходы показывать как оценку, если используются локальные тарифы; хранить дату/источник тарифа. Фактические usage и баланс не смешивать с оценкой стоимости произвольной модели.
- Формат Avito является профилем экспорта над собранными данными. Не путать экспорт файла с публикацией.
- SheetJS загружать по запросу экспорта из локального bundle. Проверить происхождение и лицензию текущего vendor-файла перед переносом зависимости.

## 6. Popup и дашборд

### Popup: контекст и одно основное действие

Ориентир: ширина 360–380 px, компактная высота по содержимому. Без горизонтальных вкладок и длинных списков.

```text
Название расширения           Настройки
Ozon · Карточка товара
Название товара
Текущая цена / статус отслеживания

[ Отслеживать товар ]

Задания: 1 выполняется
[ Открыть дашборд ]
```

Основное действие зависит от страницы: «Отслеживать» для Ozon, «Собрать товар» для поддержанного сбора, «Открыть инструменты продавца» для кабинета. Возможности не выдумываются для неподдерживаемого сайта. На другой странице показывать краткое объяснение и кнопку дашборда.

Допускается небольшой ввод целевой цены непосредственно после «Отслеживать». Настройки AI, редакторы промптов, история, экспорт, массовый ввод и таблицы полностью уходят из popup. Закрытие popup не отменяет запущенную работу.

### Дашборд: отдельная extension page

Открывать `dashboard/index.html` во вкладке расширения; при повторном открытии фокусировать существующую вкладку текущего профиля. Навигация сохраняется в hash-маршрутах, например `#/products?marketplace=ozon`. Прямая ссылка и reload возвращают нужный раздел.

Основная навигация:

- **Товары** — стартовый экран: поиск, магазин, вид данных, сортировка, сбор по артикулам и экспорт.
- **Мониторинг** — правила цены, интервал, последнее успешное наблюдение, ошибки проверки.
- **Ответы** — шаблоны, режимы генерации, подключённая seller-вкладка, черновики и результаты. Показать ограничение доступного DOM, не изображать полную серверную базу отзывов.
- **Контент** — Rich-контент Ozon и подготовка описаний Citilink для экспорта.
- **Задания** — текущие и завершённые операции, прогресс, причины остановки, безопасный повтор.
- **История** — события и уведомления с фильтрами.
- **Настройки** — магазины, мониторинг, AI, данные расширения.

Магазин — общий фильтр и контекст, а не повторяющаяся копия приложения. В неподдерживаемом сочетании показывать понятное объяснение. Настройки магазинов описывают включённые возможности и доступ; не создавать фиктивное «подключение аккаунта», когда используется текущая сессия сайта.

```text
┌────────────────┬─────────────────────────────────────────────┐
│ Название       │ Товары                     [Собрать товары] │
│                │ Поиск…     Все магазины     Статус           │
│ Товары         ├─────────────────────────────────────────────┤
│ Мониторинг     │ □ Товар       Магазин  Цена   Обновлено      │
│ Ответы         │ □ …                                         │
│ Контент        │ □ …                                         │
│ Задания · 1    │                                             │
│ История        │ Выбрано 3           Экспортировать / Удалить │
│                ├─────────────────────────────────────────────┤
│ Настройки      │ Citilink: собрано 12 из 30    Открыть задание │
└────────────────┴─────────────────────────────────────────────┘
```

Карточка товара открывается в боковой панели. Длинные промпты и настройки редактируются на странице с видимой кнопкой сохранения. Массовые действия доступны после выбора строк. Опасные действия получают подтверждение с количеством затрагиваемых элементов.

Не добавлять пустой обзор с декоративными графиками. Сначала рабочие таблицы и задачи; обзор появится, если для него будут полезные данные.

## 7. Дизайн и качество интерфейса

Применены принципы frontend-design, emil-design-eng, web-quality-audit; для предложенного React UI — переносимые рекомендации Vercel и shadcn. SEO внутренней страницы расширения не является целью. Next.js/SSR-правила здесь неприменимы.

Направление: спокойный рабочий инструмент для товаров и операций. Приоритет — читаемая таблица, ясные состояния, минимум отвлечений. Цвет магазина используется в метке, а не перекрашивает всё приложение.

Начальные токены для проверки на макете:

- Фон `#F5F7FA`, поверхность `#FFFFFF`, основной текст `#172033`, вторичный текст `#596579`, акцент `#3157C8`, граница `#D8DEE8`.
- Статусы получают отдельные семантические success/warning/error-токены и текстовые подписи. Контраст проверяется на реальных сочетаниях, а не предполагается по HEX.
- Заголовки: локальный Manrope с кириллицей; основной текст и контролы: Segoe UI / system-ui. Числа цен — tabular-nums. Не загружать шрифты с внешнего CDN.
- Основной размер 14 px, вспомогательный 12–13 px, заголовки 20–24 px. Не использовать 10–11 px для важных настроек.
- Шаг отступов 4/8/12/16/24/32 px; одинаковые высоты контролов, радиусы и плотность таблиц.
- Характерная деталь: цена всегда показана вместе с условием её получения и временем наблюдения. Условия «с банком/кошельком» видны без открытия карточки.

| Сейчас | После | Зачем |
| --- | --- | --- |
| Шесть вкладок в узком popup | Контекстная карточка и вход в дашборд | Сократить выбор при быстром действии |
| Inline-стили, отдельные брендовые кнопки, `!important` | Общие токены и варианты компонентов | Единая иерархия и предсказуемая поддержка |
| `transition: all` в popup и seller CSS | Явные свойства; короткие необязательные переходы | Избежать случайной анимации размеров и позиций |
| Placeholder вместо label у части полей | Постоянная подпись, пояснение и ошибка рядом с полем | Понятность и доступность |
| Смешаны автосохранение и кнопка сохранения | Одна модель сохранения на форму | Пользователь видит, применены ли изменения |
| Неоднородные состояния фокуса | Общий заметный focus-visible и порядок Tab | Работа клавиатурой |
| Успех массовой отправки по клику | Подтверждённый результат, ошибка или неизвестный исход | Правдивый статус операции |

Обязательные состояния: загрузка, пустой список, фильтр без результатов, ошибка, устаревшие данные, частичный результат, нет разрешения, вкладка закрыта, нет AI-ключа, неизвестный исход отправки.

Доступность: связанные labels, семантические таблицы, названия icon-кнопок, управление клавиатурой, возврат фокуса из Dialog/Sheet, `aria-live` для значимых обновлений, отсутствие передачи смысла только цветом. Проверить контраст 4.5:1 для обычного текста; поддержать reduced-motion и zoom 200%.

Проверить дашборд на ширинах 1440, 1024 и 768 px. На узкой ширине боковая навигация сворачивается, таблица имеет управляемый горизонтальный scroll, длинные значения не ломают страницу. Popup проверяется отдельно в настоящем extension popup.

Производительность: разделять bundle по поверхностям и тяжёлым функциям, подписываться только на нужные данные, освобождать observers/listeners при смене seller-маршрута. Сначала пагинация таблиц; виртуализацию добавлять по измерениям, если набор данных её требует.

## 8. Порядок реализации и критерии завершения

### Этап 1. Зафиксировать совместимость и каркас сборки

Файлы: новые package/tsconfig/Vite-конфигурация, entrypoints, tests; существующий manifest используется как исходная спецификация.

- Составить реестр текущих storage keys, message actions, экспортных колонок и сценариев.
- Сохранить обезличенные DOM-фикстуры парсеров и небольшие наборы старых данных.
- Добавить команды `typecheck`, `test`, `build`, `test:e2e`; определить минимальную поддерживаемую версию Chrome по реально используемым API.
- Собрать минимальное MV3-расширение в dist, проверить manifest, CSP, ресурсы, content scripts и service worker.
- Не переводить весь JavaScript за один проход: перенести проверяемые модули постепенно.

Готово: воспроизводимая сборка загружается в тестовом профиле Chrome, существующие сценарии перечислены, парсеры имеют исходные проверки. Рабочая установка пользователя не заменяется тестовой без необходимости.

### Этап 2. Контракты, репозитории и миграция

Файлы: `src/domain/`, `src/storage/`, `src/platform/messaging.ts`, `src/background/commands.ts`.

- Реализовать схему, валидатор сообщений, последовательные изменения, ревизии, migration/recovery.
- Перевести старые UI и виджеты на команды через временный совместимый обработчик; прекратить прямую запись общих сущностей.
- Ограничение storage-доступа вводить после перевода всех content-потребителей, чтобы не сломать настройки Seller.

Готово: сохранены старые значения; повторная и прерванная миграции безопасны; параллельное редактирование и проверка цены не теряют данные; удалённая запись не возвращается.

### Этап 3. Первый вертикальный сценарий: Ozon

Файлы: `marketplaces/ozon/consumer`, `features/tracking`, `entrypoints/dashboard`, `entrypoints/popup`, `ui`.

- Объединить Ozon-парсинг, сохранив различие типов цен.
- Построить оболочку дашборда, страницу мониторинга и новый popup.
- Проверить цепочку: карточка Ozon → отслеживание → дашборд → изменение цели → фоновая проверка → история.
- Не скрывать ещё не перенесённые функции: на промежуточной ветке использовать отдельную временную legacy-страницу, недоступную в финальной поставке.

Готово: один полный сценарий работает через новую архитектуру; есть визуальные проверки popup, таблицы и боковой панели. Это первый контрольный результат, а не несколько недель невидимого перемещения файлов.

### Этап 4. Общие задания, WB и Citilink

Файлы: `background/jobs.ts`, `scheduler.ts`, `recovery.ts`, `platform/tabs.ts`, `features/collection`, `marketplaces/wildberries`, `marketplaces/citilink`.

- Реализовать устойчивые задания и восстановление; подключить мониторинг к тому же механизму.
- Перенести WB и Citilink как адаптеры; сохранить варианты цен и правила получения фото.
- Разделить Citilink collection и AI-description; вывести частичные результаты в дашборд.
- Реализовать страницу заданий, остановку на безопасной границе и ограниченные повторы чтения.

Готово: закрытие UI и остановка service worker не теряют очередь; дублирующий запуск не создаёт гонок; ошибка одного товара не уничтожает результаты остальных; служебные вкладки освобождаются.

### Этап 5. Ozon Seller и AI

Файлы: `marketplaces/ozon/seller`, `features/replies`, `features/rich-content`, `features/ai`, страницы ответов/контента/настроек.

- Разделить `seller_content.js` на reviews, questions, rich-content, lifecycle и общие DOM-примитивы.
- При смене маршрута отключать прошлые observers, таймеры и оверлеи; не накапливать обработчики.
- Перенести шаблоны и промпты; сохранить существующие подстановки и настройки пользователя.
- Разделить генерацию, вставку и отправку; подтверждать результат сайта. Не менять существующие явно выбранные режимы отправки незаметно.
- Подключить статус seller-вкладки к дашборду. Не пытаться перенести весь DOM кабинета на страницу расширения.

Готово: генерация сама по себе не отправляет ответ; отправка требует явного запуска соответствующего действия; повтор после неизвестного исхода не выполняется автоматически; переходы SPA не дублируют UI. Live-проверки отправки выполняются отдельно, только на согласованном объекте.

### Этап 6. Экспорт, история и завершение дизайна

Файлы: `features/export`, оставшиеся dashboard routes, `ui/tokens.css`, компоненты и стили виджетов.

- Перенести XLSX-экспорт и профиль Avito; сохранить нужные колонки и корректное открытие файла.
- Довести поиск, фильтры, выбор строк, состояния ошибок и сохранение настроек.
- Привести popup, дашборд и виджеты к общей дизайн-системе с изоляцией стилей сайта.
- Провести проверку клавиатуры, контраста, responsive, reduced-motion и реальных скриншотов.

Готово: все исходные возможности доступны, настройки не спрятаны в popup, библиотеки экспорта отсутствуют в начальном popup bundle.

### Этап 7. Удаление старых путей и финальная проверка

- Удалить legacy UI, старые entrypoints и совместимые обработчики только после миграции всех их потребителей.
- Проверить отсутствие ссылок manifest/build на старые файлы и отсутствие дублирующих listeners/парсеров.
- Обновить документацию внутри `MarketPilot/`: сборка, установка dist, добавление магазина, проверка миграций. Не менять корневые правила вне разрешённой области.
- Добавить тестовый магазин только в тестовую сборку как доказательство расширяемости существующих capabilities.
- Выполнить полную проверку и перечислить оставшиеся ограничения. Релиз/версия/публикация — отдельная авторизация.

Готово: единственные владельцы состояния и сценариев подтверждены тестами; legacy-код не нужен для работы; новый адаптер проходит общий сценарий без изменений ядра.

## 10. Основные решения и риски

- Перенос по вертикальным сценариям снижает риск полной остановки проекта. Нельзя поддерживать старое и новое хранилище как два равноправных источника истины.
- Обобщать подтверждённые повторы: очередь, сообщения, экспорт, UI-состояния. Не заставлять Rich-контент и сбор цен реализовывать искусственно одинаковые методы.
- Сайты меняют DOM; селекторы и фикстуры локализуются в адаптере, но не устраняют необходимость живой проверки.
- Восстановление чтения и восстановление публикации различаются. Для публикации важнее исключить дубликат, чем автоматически продолжить любой ценой.
- Перенос настроек важнее смены названия расширения. Рабочее название можно оставить до отдельного выбора бренда.
- Разрешения новых доменов добавляются осознанно. Не расширять доступ до всех сайтов ради удобства реестра.
- Начальное направление дизайна и React/TypeScript-стек — предложения плана. Макет первого рабочего сценария проверяется до переноса всех экранов.

Порядок зависимостей: каркас → данные/контракты → первый Ozon-сценарий → устойчивые задания и остальные магазины → Seller/AI → завершение UI/экспорта → удаление legacy.
